# 企画の複数画像・後から追加した画像の永続保存（23.30）

現状追記（2026-08-29）: 以下はPR #11実装時の履歴。現在はmainへマージ済みで、本番にも `idea_images` と7引数の保存RPC・参照保護policyが存在する。23.31の週間予定更新ではこのSQLを再実行しない。現在の監査・検証は [ARCHITECTURE](ARCHITECTURE.md) と [23.31検証記録](weekly-schedule-verification.md) を参照。

## 根本原因と本番確認（2026-08-28）

- 最新main `8ce53b3136b8e3fdc77d2344b29ff1b23337865d` は23.28の1枚保存版。複数画像対応のPR #11はopen・未マージであり、mainに含まれていない。未マージの理由について、レビュー判断などは推測しない。
- mainの追加・編集は単一の `imageFile` をアップロードし、`ideas.image_url` / `idea_items.image_url` に新URLを代入する。再取得もこの1カラムだけなので、後からBを保存するとAへの参照が置換される。Storageの同一path上書きが原因ではない。
- 接続済みSupabase `jyxrrnfnypqaecfojsle` で、`idea_images` と `save_idea_with_images` RPCが存在しないことを確認した。migration履歴も空。PRにあるSQLは本番未適用であり、似たテーブル・追加の移行SQLは作らずPR #11の既存migrationを修正する。
- `ideas.id` はUUID、`idea_items.id` はbigint、`parent_idea_id` はtext。両テーブルは既存の認証済み共同管理RLSを使用する。新テーブルには各親型に合った外部キーを追加する。
- 公開 `idea-images` バケットは既存7オブジェクト・7個の別path。旧 `image_url` を持つ企画内アイデアは3件。確認・テスト前後でこの件数は変わっていない。旧画像を推測で再割り当てしたり、既存URLをNULL化したりしない。
- 未マージ版のUIはすでに複数選択を配列へ追加していたが、既存・追加・削除予定の区別と同一ファイル判定が不十分で、RPCもクライアントの完成画像一覧を保存対象としていた。今回、UIとDBの両方を明示的な追加／削除指定にする。

## 構造と互換性

- 対象は `ideas`（企画）と `idea_items`（企画内アイデア）。既存の `image_url` と `idea-images` バケットを維持する。
- `idea_images` を1対Nの関連テーブルとして追加。企画の UUID または企画内アイデアの bigint の片方だけを親に持ち、URL・Storage path・追加順を保存する。
- 既存画像の一括移行・削除・NULL化は行わない。旧 `image_url` は読み取りフォールバックとして表示し、次に明示保存された際も同じURLのまま扱う。新規アップロードは不要。
- 明示保存時のみ、`image_url` に先頭画像を反映する。全画像を取り除いて保存した場合のみ、その対象レコードを画像なしにする。
- 認証済みユーザーが共同管理する現行RLSに合わせる。新テーブルの匿名読み書きと、未認証での保存RPC実行は許可しない。

## 追加・編集・表示

- 企画・企画内アイデアとも最大10枚。複数同時選択、保存前プレビュー、既存画像を残した追加、1枚ずつの取り除きに対応する。
- `existingImages` / `pendingImages` / `removedImages` を分離する。FileListを再選択してもpending配列へ追記し、保存済み画像は再アップロードしない。キャンセルはDB/既存Storageを変更しない。
- 同一選択ファイルの `name / size / lastModified / type` が一致する場合は重複追加を抑止する。同名でも更新日時などが異なる別ファイルは選択可能。保存済みURLと新規ファイルの画像内容を推測比較する処理は追加しない。
- 「保存予定 N枚（追加 M枚・削除 R枚）」をプレビューに表示する。既存8枚＋新規5枚なら2枚だけ追加し、超過3枚をスキップしたことを表示する。
- 画像なしは空枠なし。1枚は従来の表示を維持。2枚以上は一覧を最大4枠に収め、5枚以上は3枚＋残り枚数で表示する。
- 詳細は全画像を縦に並べ、モーダル全体でスクロールする。縦横比維持・contain表示で切り抜かず、小さい画像は拡大しない。
- 既存のファイルサイズ方針は変更しない。アップロードは逐次実行、ローカルプレビューはObject URLを使い、終了時に解放する。

## 保存と削除の順序

1. 新しく選択した画像だけを既存バケットの `ideas/` または `idea-items/` にアップロードする。従来の時刻＋乱数の別pathと `upsert: false` を維持する。
2. `save_idea_with_images` RPCに `p_added_image_urls` と `p_removed_image_urls` を渡す。編集開始時の画像一覧と更新日時は競合検知専用で、全画像置換には使わない。
3. RPCがDBの保存済み画像を再取得・親行ロックし、「保存済み−明示削除＋新規追加」を計算する。削除指定の行だけDELETEし、残す画像行はIDを保持したまま並び順を更新、新しい画像行だけ追加する。親レコード・先頭画像・関連行は同一トランザクションで確定する。
4. DB保存成功後、明示的に取り除いた画像だけをStorage APIで削除する。

空のFileListや追加0枚を全画像削除と解釈しない。AへB/Cを追加してもlegacy `image_url` はAのまま。Aそのものを明示削除した場合だけ、次の先頭画像に切り替わる。

途中のアップロード失敗・DB失敗では新規アップロードを後片付けし、元の画像は残す。編集開始時の画像一覧・更新日時を比較し、別ユーザーの更新があれば上書きせず再読み込みを案内する。既存の企画移動RPCにも関連画像の引き継ぎだけを追加した。

StorageのDELETE権限は、アプリ生成パスかつ全企画・企画内アイデア・画像関連行のどこからも参照されていない画像だけに限定する。ゴミ箱内や別レコードからの参照も保護する。保存レスポンスが失われても、DBに確定した画像はこの権限で削除を防ぐ。

後片付けの通信失敗は端末内の再試行キューに残し、次回画像保存時に再試行する。ブラウザ保存領域が利用できない場合はメモリ内に保持する。通信断・端末終了による孤立ファイルを完全に排除するバックグラウンドGCは追加していない。他プロジェクトや外部URLの画像は自動削除しない。

親レコードが同じトランザクションで更新されるため、既存のRealtime購読・再読み込みをそのまま利用する。Auth/PWA復帰、YouTube、通知トリガー、報酬、実績、月次処理には変更しない。

## PR #11当時のMerge後の反映（未導入環境のみ）

1. 新フロントエンドで保存を始める前に、Supabase SQL Editorで `supabase/migrations/20260827110343_multi_idea_images.sql` を実行する。既存のbaseline SQLを再実行する必要はない。
2. 新しいフロントエンドを公開し、開いているPWAを完全終了して再起動する。

新しいバケットやSecret設定は不要。Edge Function再Deploy・Cron変更は不要。本PRでは本番publicスキーマへのmigration適用、実Storageへのアップロード／削除を行っていない。`tests/fixtures/idea-images-append-check.sql` はロールバック専用のテストであり、ユーザーが本番で実行するSQLではない。

SQL未適用時も従来の企画画像の読み取りへフォールバックするが、複数画像を誤って失わないよう企画の保存はSQL適用を案内して停止する。SQLを先に適用する手順を守ること。
